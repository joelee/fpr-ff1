## Executive summary

`v2.0.0rc1` adds an opt-in compiled backend (`FF1(..., backend="rust")`): a PyO3 extension `fpr_ff1._rs` implementing SP 800-38G Algorithm 7 and the Algorithm 6 PRF over RustCrypto `aes`, dispatched from Python *after* the unchanged `_prepare` validation so exception types and messages are identical on both backends. The change also adds `BackendError`, a test-only trace bridge so the per-round intermediate suite runs on both cores, abi3-py312 platform wheels for five targets, a pure-Python sdist fallback, `cargo-audit` in CI, and a 2.0 documentation set.

The port itself is good. `lib.rs` mirrors `_ff1.py` step for step, carries every "plausible but wrong" gotcha from `AGENTS.md` as a code comment, and I found no divergence from the reference by reading: `b` from `v`, `pad = (-t-b-1) mod 16` via `rem_euclid`, `S` truncated to `d` bytes, `CIPH_K(R XOR [j]^16)` as a single block, the decrypt subtraction done non-negatively, and the parity rule shared. Locally, with the extension built, the full suite is green: **1,403 passed, 100% line and branch coverage**, all nine NIST samples and all 90 rounds of intermediates bit-exact on both backends, the FIPS 197 KAT and PRF-equality checks green, `cargo test` 8/8, and ruff/pyright clean. The pure-Python path is byte-identical to 1.1.0 (the frozen KAT, interoperability, and bijectivity suites are unmodified and pass).

The blocking problem is that none of that dual-backend evidence reaches the release gate. The CI quality matrix installs the project without building the extension and never sets `FPR_FF1_REQUIRE_RUST_BACKEND`, so `conftest.py` silently parameterises over `["python"]` only. The CI log for this exact commit reads `collected 857 items / 1 skipped … 854 passed, 4 skipped`, against 1,403 locally; the only Rust execution in the whole pipeline is a single NIST-sample smoke test in `wheel-test-platform`, and `cargo test` is not invoked by any job. The AES KAT, the PRF-equality test, the `d > 16` S-expansion differential cases, and the per-round intermediates are therefore unverified for every wheel CI publishes. The `CHANGELOG` and README claim the entire suite runs against both backends; it does on the maintainer's machine, not in the gate. This is `REV-00006-MAJ-01` and it is the same class of "silent skip looks exactly like a pass" hazard the project already guards against for the differential oracle with `FPR_FF1_REQUIRE_ORACLE`.

One Medium: the PyO3 bindings never release the GIL, so the "accelerated" backend gives no thread-level parallelism (measured 0.91× with 4 threads on 32 cores) and, at long inputs, holds every other Python thread for up to ~125 ms per call — a latency regression for exactly the "share one `FF1` across request threads" use case the README endorses. Seven Lows cover documentation drift (including a crossover claim that is off by roughly an order of magnitude — in the conservative direction), a per-round AES key-schedule rebuild in the Rust core, a missing `cargo` Dependabot ecosystem, a pickle-boundary revalidation gap, a hard-coded extension version, and Rust-side hygiene gates.

>   Locally with the extension built the same command collects **1,403** tests — a `pytest --collect-only` count shows **546** are Rust-parameterised (NIST vectors ×3 modes, 90 rounds of intermediates, frozen KAT, differential incl. the seven `d > 16` S-expansion transitions, interoperability, properties, bijectivity, thread-safety, pickle, and the 19 FIPS-197/PRF checks). > - **Failure or attack scenario:** A future change to `lib.rs` — say, the `j` counter in the step 6.iii expansion (`lib.rs:302-309`) starting at 0, or `cipher_block` accidentally becoming a one-block CBC-MAC over `R || j` — passes CI green: NIST sample 2 has `d = 12` and never enters that branch, `cargo test` does not run, and the 546 tests that would catch it are skipped. `publish.yml` reuses this gate as its release condition, so the broken wheel is published to PyPI with provenance attestations vouching for it.

One Linux x86_64 leg is sufficient for conformance; the platform-wheel smoke test can remain as the "wheel is importable" check. Add `cargo test --manifest-path rust/Cargo.toml` (and see LOW-07) to the same leg. Make `publish.yml`'s gate depend on it (automatic if it lives inside `ci.yml`).
> - **Suggested verification:** On a branch, deliberately break `lib.rs` (e.g. start `j` at 0) and confirm the new leg goes red while every existing job stays green; then revert. Assert the collected count in the leg (`pytest --collect-only -q | tail -1` ≈ 1,403) so a regression back to 857 is visible.

### Medium

#### REV-00006-MED-01 — The PyO3 bindings hold the GIL for the entire FF1 call

- **Location:** `rust/fpr-ff1-rust/src/lib.rs:386-396` — `encrypt_numerals` / `decrypt_numerals` `#[pyfunction]`s
- **What:** Both bindings take fully-owned Rust values (`Vec<u8>`, `u32`, `Vec<u16>`) and call `ff1(...)` directly without `Python::detach` (pyo3 0.29's GIL-release API, present at `pyo3-0.29.2/src/marker.rs:562`). The whole ten-round computation, including all big-integer conversions, runs with the GIL held.
- **Why it matters:** Two concrete consequences for the documented use cases. (1) *No parallelism*: the "accelerated backend for high-throughput callers" cannot use more than one core from threads — measured on this machine (32 cores, n=5,000, 4 threads × 20 calls each): `rust … serial 0.71 s, 4 threads 0.78 s, speedup 0.91×`. A `ProcessPoolExecutor` is the only way to scale, and pickling the instance ships the key (`SECURITY.md:53`). (2) *Latency stalls*: Python's 5 ms switch interval cannot pre-empt a native call, so one `encrypt_numerals` at n=20,000 (125 ms measured, `benchmarks`/this review) freezes every other thread — request handlers, health checks, logging — for the full duration. The pure-Python path, by contrast, yields every 5 ms. The README (`README.md:354-360`) tells web services to "freely share one `FF1` across request threads" and does not qualify this for the Rust backend.
- **Evidence:**
  ```rust
  // rust/fpr-ff1-rust/src/lib.rs:388-390
  fn encrypt_numerals(key: Vec<u8>, radix: u32, x: Vec<u16>, tweak: Vec<u8>) -> PyResult<Vec<u16>> {
      ff1(&key, radix, &x, &tweak, true).map_err(PyValueError::new_err)
  }
  ```
  ```text
  # GIL probe, this review (CPython 3.12.13, Linux, 32 cores; contention from a concurrent test run)
  python n=5000: 5.2 ms/call; serial 0.42s, 4 threads 0.50s, speedup 0.83x
  rust   n=5000: 8.9 ms/call; serial 0.71s, 4 threads 0.78s, speedup 0.91x
  ```
- **Suggested fix:** Add a `py: Python<'_>` parameter and wrap the core call: `py.detach(|| ff1(&key, radix, &x, &tweak, true)).map_err(...)`. Nothing inside `ff1` touches Python objects, so this is safe by construction; the stateless-core argument in `docs/configuration.md:46` is exactly what makes it sound. Re-run the thread-safety suite (it should now exercise true concurrency) and the GIL probe (expect ~3.5–4× at 4 threads). If the maintainer prefers *not* to release the GIL, document the stall in the README Backends/Thread-safety sections so callers can size inputs accordingly.

#### REV-00006-LOW-02 — Published backend guidance is radix-10 only and the stated crossover is ~10× too low

- **Location:** `README.md:253-268` — Backends table and "crossover is somewhere around a few hundred numerals"; `CHANGELOG.md:23-25`
- **What:** The README recommends the Rust backend "for short inputs" and states the crossover to the pure-Python path is "somewhere around a few hundred numerals", with a table at n ∈ {6, 100, 20 000} for radix 10 only. Measured in this review (median of 7 batches, CPython 3.12.13, Linux x86_64, release extension), the Rust backend is still *faster* at n=1,000 on every radix tried and the crossover lies between n=1,000 and n=5,000:

  | radix | n=300 | n=1,000 | n=5,000 | n=20,000 |
  |---|---:|---:|---:|---:|
  | 10 | rust 0.37× of python | 0.59× | 1.69× (slower) | 4.68× (slower) |
  | 256 | 0.25× | 0.45× | 1.63× | 6.01× |
  | 65535 | 0.37× | 0.68× | 1.91× | 4.00× |

  (`rust/python` time ratio; < 1 means Rust is faster.)
- **Why it matters:** The claim errs in the conservative direction, so no one is harmed by following it, but it is a published performance statement that does not match measurement, and it hides that at radix 256 (where the Python path is O(n)) the long-input penalty is *larger* than the radix-10 number shown. Plan `AC-12` requires README numbers to be "stated against recorded measurements".
- **Suggested fix:** Replace "a few hundred numerals" with the measured band ("between roughly 1,000 and 5,000 numerals on the reference hardware; measure with `just bench`"), add one non-radix-10 row (256 is the informative one), and extend `benchmarks/timing.py::backend_comparison_table` with n=1,000 and n=5,000 so the crossover is reproducible rather than interpolated.

#### REV-00006-LOW-03 — The Rust core rebuilds the AES key schedule ten times per call, plus once per S-expansion block

- **Location:** `rust/fpr-ff1-rust/src/lib.rs:88-89` — `prf` (`Aes::new(key)?` per call); `:116-117` — `cipher_block` (same); call sites `:290`, `:307`
- **What:** `prf` and `cipher_block` take the raw key and construct the `Aes` enum (key expansion) on every invocation. Per FF1 call that is 10 schedules for the PRF plus one per expansion block; at radix 10, n=20,000 (`d = 8312`) that is ≈ 5,190 additional key expansions per call. The README (`:262-264`) credits the compiled core with "eliminat[ing] the per-call cipher-context construction" — it moves it inside the round loop instead. The Python path expands the key once per `Cipher(...).encryptor()` too, so this is not a regression, but it is a constant factor left on the table in the one regime the backend exists for.
- **Suggested fix:** Build `Aes` once in `ff1_impl` and pass `&Aes` to `prf`/`cipher_block` (keep thin key-taking wrappers for the test-only bindings). The result is still stateless and thread-safe (the schedule is immutable and call-local). Measure n=6/100 before and after with `just bench`; a few-percent to ~20% gain at n=6 is plausible on software AES.

#### REV-00006-LOW-04 — Dependabot does not watch the Rust lock file

- **Location:** `.github/dependabot.yml:1-20`; `docs/developer-guide.md:160-161`
- **What:** The Dependabot configuration lists `github-actions` and `uv` only; there is no `cargo` ecosystem entry for `/rust`. `cargo audit` in CI (`ci.yml:100-103`) will turn the gate red when an advisory lands against `aes`, `num-bigint`, `pyo3`, or a transitive crate, but nothing will raise the remediation PR, and the developer guide's statement that "Dependabot raises PRs when a pinned action or a dependency moves" is now false for half the supply chain.
- **Suggested fix:** Add `- package-ecosystem: cargo`, `directory: /rust`, weekly, grouped like the others. Keep `Cargo.lock` committed (it is) so the PRs are lock-only bumps.

#### REV-00006-LOW-05 — `__setstate__` re-validates the key's type but not its length, so a corrupt pickle can raise outside `FF1Error`

- **Location:** `src/fpr_ff1/_ff1.py:307-338` — `FF1.__setstate__`
- **What:** The unpickle path guards `isinstance(key, bytes)` and the `_backend` value, then calls `algorithms.AES(key)`. A hand-edited state with a 15-byte (or 0-byte) key raises `cryptography`'s `ValueError("Invalid key size …")`, not `KeyLengthError`; `_radix`, tweak bounds and alphabet tables are not re-checked at all. `test_contract.py` promises every rejection is typed, and `docs/reviews/00003` H3 explicitly motivated the existing type check by the same argument ("would otherwise surface later as an opaque cryptography error").
- **Why / Suggested fix:** Pickle is trusted input and `SECURITY.md` already frames it as the caller's boundary, so impact is limited to a misleading exception type. The smallest fix is to add `if len(key) not in {16, 24, 32}: raise KeyLengthError(...)` next to the type check, plus a test in `test_pickle.py` mirroring `test_setstate_rejects_non_bytes_key`. (A fuller option: route the state through the same `_require_*` helpers `__init__` uses.)

#### REV-00006-LOW-06 — `_rs.__version__` is a hard-coded literal unrelated to the distribution version and untested

- **Location:** `rust/fpr-ff1-rust/src/lib.rs:384`; `rust/fpr-ff1-rust/Cargo.toml:3`
- **What:** `m.add("__version__", "0.1.0")` is a string literal; the crate version is also `0.1.0` while the wheel it ships in is `2.0.0rc1`, and the wheel's embedded SBOM (`dist-info/sboms/fpr-ff1-rust.cyclonedx.json`) will report the crate as `0.1.0` forever unless someone remembers two places. No test reads the attribute.
- **Suggested fix:** Either drop the attribute (nothing consumes it) or use `env!("CARGO_PKG_VERSION")` and bump `Cargo.toml` in lock-step with `pyproject.toml` (add a one-line assertion to `test_backend_dispatch.py` that `_rs.__version__` equals the crate version recorded in `Cargo.toml`, or that it equals `fpr_ff1.__version__` if you choose to align them).

#### REV-00006-LOW-07 — Rust-side hygiene gates are absent: no clippy/fmt in `just quality` or CI, two clippy warnings, a needless `allow`, and a Linux/macOS-only dev recipe

- **Location:** `justfile:61` (`quality`), `:86-107` (`rust-test`, `backend-dev`); `rust/fpr-ff1-rust/src/lib.rs:186`, `:234`, `:239`; `.github/workflows/ci.yml` (no `cargo clippy`/`cargo fmt --check`)
- **What / Why / Suggested fix:**
  - `cargo clippy --all-targets` on this commit emits `manual_div_ceil` at `lib.rs:234` and `:239` (and twice in `tests.rs`). These are stylistic, but the Python side enforces ruff + pyright strict on every checkpoint while the Rust side has no equivalent gate, so warnings will accumulate silently. Add `cargo fmt --check` and `cargo clippy --all-targets -- -D warnings` to the Rust CI leg introduced for MAJ-01 (and a `just rust-lint` recipe). Note: prefer keeping the explicit `(b + 3) / 4` form with an `#[allow]` and a spec-step comment if you judge `div_ceil` less line-by-line comparable to SP 800-38G — the decision should be recorded either way.
  - `#[allow(clippy::too_many_arguments)]` at `lib.rs:186` guards a five-argument function; clippy's threshold is seven. Remove it.
  - `just backend-dev` (`justfile:102-105`) copies `lib_fpr_ff1_rs.so`/`.dylib` only; on Windows the artifact is `_fpr_ff1_rs.dll` and must land as `_rs.pyd`, so the documented dev loop (`docs/developer-guide.md:97-98`) does not work on one of the three CI platforms. Either add the Windows arm or state the limitation in the guide.

## Open questions

1. **Should the Rust core adopt the divide-and-conquer conversion?** The backend is 4–6× slower than pure Python at n=20,000 across radices (LOW-02 table) because `num_radix`/`str_radix` in `lib.rs:127-153` are the quadratic reference loops — a recorded STEP-08 bounded decision. Porting `_num_radix_split`/`_str_radix_split` (and the pow2 byte-packing path) would very likely make the Rust backend dominant at every length and remove the need for crossover guidance entirely. Resolved by a half-day measurement, not by review; worth deciding before `v2.0.0` final since it changes the README's recommendation.
2. **Is `Development Status :: 5 - Production/Stable` intended on an `rc1` upload?** `pyproject.toml:30`. PyPI renders it on the rc page. Many projects keep it; flagging only because the project has been careful about calibrated claims elsewhere.
3. **Tag format.** `publish.yml:62-68` requires the release tag to equal `v` + `project.version`, i.e. exactly `v2.0.0rc1`. The plan's STEP-15 commit subject says "release v2.0.0-rc1" (hyphenated). Confirm the tag will be `v2.0.0rc1` or the publish job will refuse.
4. **`cargo audit` status at this commit** — not run locally (`cargo-audit` is not installed here); the CI `Dependency audit` job on run `34212028752` succeeded, which is the authoritative evidence.
