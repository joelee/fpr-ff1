## Executive summary

Plan 00006 turns review 00007's four findings and twenty-item stable-release checklist, plus three user decisions (ship the Rust divide-and-conquer conversion in 2.0; cut `rc2` first; keep the `manylinux_2_34` floor), into twelve requirements and twelve steps ending in a published `v2.0.0`. I verified each defect requirement against the code at `26b0164`:

- **REQ-01 (MAJ-01)** is real and correctly scoped. `FF1.__setstate__` (`src/fpr_ff1/_ff1.py:310-352`) validates `state.get("_backend", "python")` but never assigns `self._backend`; both numeral methods read it unconditionally (`:484`, `:506`); and `test_legacy_pickle_state_defaults_to_python` (`tests/test_backend_dispatch.py:251-261`) hides this by constructing its destination with `FF1(key=_KEY, radix=10)`, which supplies the attribute real unpickling lacks.
- **REQ-02 (MED-01)** is real: `lib.rs:301` writes `(t as u32).to_be_bytes()` while `_validate_tweak` (`_ff1.py:367-371`) checks only configured bounds and `_encode_uint(t, 4)` (`:813`) raises `OverflowError` — outside `FF1Error` — at `t ≥ 2**32`.
- **REQ-03 (LOW-01)** names real direct constructions (`tests/test_validation.py:246-435`, `tests/test_interoperability.py:109-124`).
- **REQ-06 (MED-02)** is real: `wheel-test-platform` (`ci.yml:329-347`) downloads only `wheels-x86_64-unknown-linux-gnu` on `ubuntu-latest`, and `rust-conformance` builds with plain `cargo build` (no `pyo3/abi3-py312`), so the full suite runs on a non-abi3 source-tree extension.

The sequencing is sound (defect fixes → Rust core → measurement → CI → docs → release mechanics), the cross-cutting table and stop conditions are specific, and front-matter counts match the body (12/12/12). Three things stop me approving it as written.

**The blocking one is a process defect that would propagate into a published policy.** Decision D4 says the 1.x support window is "resolved in STEP-08 by documenting the actual policy; the concrete window is a documentation decision the plan makes explicit (see REQ-08)". REQ-08 does not make it explicit — it instructs the Builder to "state the actual 1.x maintenance window" without saying what it is. `SECURITY.md` currently contradicts itself ("the latest `2.x` release receives fixes" above a table marking `1.0.x` and `1.1.x` supported), so there is no existing policy to transcribe. A support window is a maintainer commitment; the plans contract forbids converting an unresolved question into a requirement, and `blocking_decisions: 0` is therefore misreported. This is `REV-00008-MAJ-01`.

The two Mediums are gaps that would make the Builder stall or guess at a load-bearing point: no step hands `v2.0.0rc2` to the owner for tagging, publication and soak (STEP-11's precondition "rc2 candidate published or otherwise available for review" has no owner), and STEP-06 omits runner labels, the venv-isolation recipe that keeps `src/` off `sys.path`, and the flags that make the abi3 full-conformance leg equivalent to `rust-conformance`. A third Medium: REQ-02 drops the configured-bound interaction review 00007 explicitly required ("define how configured bounds interact with that ceiling without silently clamping"). Three Lows cover a missing performance decision rule for the Rust conversion, a stronger structural test for the `__setstate__` drift class, and three checklist sub-items that did not survive the review-to-plan translation.

> - **Category:** Documentation / Release policy (plan integrity)

At STEP-08 the Builder must write a concrete sentence into `SECURITY.md` — "1.1.x receives security fixes until …" — and has no source for it. Either it stalls (a deviation entry, user round-trip mid-plan) or it picks something plausible (e.g. "until 2.1.0" or "for six months") and the maintainer discovers a support commitment they did not make after `v2.0.0` ships with it.

Once chosen, write the exact `SECURITY.md` sentence and table into REQ-08 so STEP-08 is transcription, not policy-making. Also fix the `1.0.x` row now contradicting the prose, whichever option is chosen.
> - **Suggested verification:** After amendment, REQ-08 contains the literal support sentence and table rows; `blocking_decisions` equals the number of `open` rows in §7; approval is recorded only after D4's row shows a user resolution.

#### REV-00008-MED-01 — No step hands `v2.0.0rc2` to the owner for tagging, publication and soak; STEP-11's precondition is unowned

- **Location:** `docs/plans/00006-Review_00007_to_v2.0.0.md` §11 STEP-09 (cuts the rc2 *version*), STEP-10 (gates it), STEP-11 preconditions ("rc2 candidate published or otherwise available for review"); §7 D2; review 00007 `STABLE-13`
- **What:** User decision D2 is "cut `v2.0.0rc2` first", and STABLE-13's done-condition is "the corrected/optimized candidate has green artifact tests, **its own immutable release evidence**, and representative consumer smoke results … the owner sets any soak duration". The plan bumps the version (STEP-09) and runs the gate (STEP-10), then STEP-11 assumes the candidate is "published or otherwise available" — but no step, hand-off line, or acceptance criterion says the owner tags `v2.0.0rc2`, that `publish.yml` runs against it, that the PyPI release is verified (as STEP-12 does for final), or how long the soak is. "Otherwise available for review" also quietly permits skipping publication altogether, which would make D2 a version-string change rather than a candidate.
- **Why it matters:** The rc2 exists to soak the Rust conversion and the wheel-matrix change on real installs before final. Without an owner hand-off point the Builder either stops at STEP-10 with nothing to escalate against, or proceeds to STEP-11 and the final bump on the strength of CI alone — the exact "promote by changing version strings" path review 00007 warned against. The `[2.0.0rc2]` changelog section also needs a date, which is the tag date.
- **Evidence:**
  ```markdown
  ### PLAN-00006-STEP-11 — Obtain a re-review and bump to final
  - **Preconditions:** STEP-10 green; rc2 candidate published or otherwise available for review.
  ```
  versus §16: "tag `v2.0.0` (exactly), push, and GitHub release remain the user's" — the rc2 tag is never mentioned in §16 at all.
- **Suggested fix:** Insert an explicit owner hand-off between STEP-10 and STEP-11 (a STEP-10b, or a task at the end of STEP-10): Builder records the frozen rc2 commit and evidence; owner tags exactly `v2.0.0rc2` and publishes a **pre-release**; `publish.yml` runs; Builder verifies the PyPI release the same way STEP-12 does for final (seven-file set, attestations, clean-environment install, NIST + `d > 16` smoke on both backends); owner states the soak window (or explicitly waives it) in the work log. Make STEP-11's precondition "rc2 published and verified per that step", and add an AC (or extend AC-09) for it. List the rc2 tag in §16 alongside the final tag.

#### REV-00008-MED-02 — STEP-06 is under-specified on the details that decide whether the gate tests the artifact or the source tree

- **Location:** `docs/plans/00006-Review_00007_to_v2.0.0.md` §9 `PLAN-00006-REQ-06`; §11 STEP-06 tasks 1–3 and verification; `.github/workflows/ci.yml:78-135` (`rust-conformance`), `:329-373` (`wheel-test-platform`); `tests/conftest.py:12`, `tests/test_exact_arithmetic.py:17-18`
- **What:** Three things the Builder must get right are left to inference:
  1. **Runner labels.** The plan says "a native Intel macOS runner or an explicitly configured compatible environment for the cross-built Intel wheel" without naming one. GitHub currently offers Intel labels `macos-15-intel` and `macos-26-intel` (and paid `-large` variants); `macos-14-large` is deprecated and `macos-13` is gone. Naming `macos-15-intel` (plus `ubuntu-24.04-arm`, `macos-latest` for arm64, `windows-latest`) removes a research step and a plausible wrong choice (a `-large` label bills differently).
  2. **Isolation of the abi3 full-conformance leg.** The existing pattern (`uv venv wheel-check-rs` + `uv pip install … *.whl` + `wheel-check-rs/bin/python`) is right for a smoke script, but the full suite needs `pytest`, `hypothesis`, `pytest-cov`, `packaging` and the oracle (`ubiq-security-fpe` plus the repo's `tests/_oracle` shim). If the Builder reaches for `uv run`/`uv sync`, the editable project is reinstalled over the wheel and the leg silently tests the source tree — the MAJ-01-of-review-00006 class again. The plan's "deliberate import-origin assertion" is the right safeguard but is mentioned only under *test-or-evidence-first*, not as a task with a concrete check (`fpr_ff1.__file__` under the venv's `site-packages`, and `fpr_ff1._rs.__file__` ending in `_rs.abi3.so`/`.pyd`). The recipe should be stated: `uv export --frozen --no-emit-project --format requirements-txt` (dev group) → `uv pip install --python <venv> -r … dist-wheels/<wheel>` → run `<venv>/bin/python -m pytest` from the checkout so `tests/_oracle` and `tests/test_exact_arithmetic.py`'s source-path read (`parents[1]/src/fpr_ff1/_ff1.py`) still resolve while `src/` stays off `sys.path` (it is not on it: `tests/__init__.py` makes pytest insert the repo root, not `src/`).
  3. **Flags.** The abi3 leg must carry `FPR_FF1_REQUIRE_RUST_BACKEND=1`, `FPR_FF1_REQUIRE_ORACLE=1`, the `-k rust ≥ 500` floor and `--cov-fail-under=100` to be equivalent to `rust-conformance`; the plan lists none of them for STEP-06 (they appear only in the §10 checkpoint command, which is the source-tree gate).
  Also unstated: the per-target subset across 3.12/3.13/3.14 is 15 jobs; whether that is 15 legs or a per-target matrix is a cost decision the plan should make.
- **Why it matters:** REQ-06 exists because the previous gate looked like it tested the wheels and did not. A leg that runs the full suite against the editable source while a wheel sits installed beside it reproduces that failure with a green badge.
- **Evidence:**
  ```yaml
  # ci.yml:329-347 — the only installed-native-wheel execution today
  wheel-test-platform:
    runs-on: ubuntu-latest
    ...
          name: wheels-x86_64-unknown-linux-gnu
  ```
- **Suggested fix:** In STEP-06 tasks, name the runner labels per target; add an explicit task "install the wheel plus exported dev requirements into a fresh venv, never `uv sync`/`uv run` in that leg"; add the import-origin assertion as a numbered task with the two `__file__` checks; carry the four flags into the abi3 leg; decide the Python-version fan-out. Add a stop condition: "the import-origin assertion resolves to the checkout — escalate".

#### REV-00008-MED-03 — REQ-02 drops the configured-bound interaction review 00007 required, and leaves the sibling `n as u32` cast unchecked

- **Location:** `docs/plans/00006-Review_00007_to_v2.0.0.md` §9 `PLAN-00006-REQ-02`; §11 STEP-02 tasks 1–2; `src/fpr_ff1/_ff1.py:61-97` (`_validate_tweak_bounds`), `:367-371`; `rust/fpr-ff1-rust/src/lib.rs:300-301`
- **What:** Review 00007 MED-01's suggested fix reads "define how configured bounds interact with that ceiling without silently clamping". REQ-02 specifies only the per-tweak ceiling. Today `_validate_tweak_bounds` accepts any non-negative integers, so after STEP-02 as written: `FF1(..., min_tweak_len=2**32)` constructs successfully but no tweak can ever satisfy it (the same "unusable instance" `_validate_tweak_bounds` was written to prevent for inverted bounds), and `max_tweak_len=2**40` is accepted and silently means `2**32 - 1` — a clamp by omission. Separately, `lib.rs:300` casts `n as u32` exactly as `:301` casts `t`; `n` is bounded by `_MAX_LEN` in Python so it is not a live defect, but STEP-02 task 2 converts only `t`, leaving the two identical casts inconsistent in a core whose whole review posture is line-by-line comparability.
- **Why it matters:** The ceiling is being added precisely to make rejection explicit and identical; leaving the bounds path able to admit an unsatisfiable or silently-capped configuration recreates the "plausible but wrong" class one layer up. The `n` cast is a five-token change that makes the defence-in-depth claim true rather than half-true.
- **Evidence:**
  ```python
  # _ff1.py:85-95 — only non-negativity and low <= high are checked
  for name, bound in (("min_tweak_len", low), ("max_tweak_len", high)):
      if bound is not None and bound < 0:
          raise TweakLengthError(...)
  if low is not None and high is not None and low > high:
      raise TweakLengthError(...)
  ```
  ```rust
  // lib.rs:300-301
  p_block.extend_from_slice(&(n as u32).to_be_bytes());
  p_block.extend_from_slice(&(t as u32).to_be_bytes());
  ```
- **Suggested fix:** Extend REQ-02: (a) `_validate_tweak_bounds` rejects `min_tweak_len > 2**32 - 1` (unsatisfiable) and `max_tweak_len > 2**32 - 1` (exceeds the encodable ceiling — reject rather than clamp, with a message naming the ceiling), at construction; (b) both `n` and `t` use `u32::try_from(..).map_err(..)` in `lib.rs`; (c) add the two constructor cases to `tests/test_contract.py::_malformed_calls` and `tests/test_validation.py`; (d) document the ceiling in `docs/configuration.md` §Runtime constraints as a new rejection (it is a SemVer-relevant input-domain change — the changelog entry in STEP-09 must say so, per the project's version policy). Note that the ceiling value is `2**32 - 1` inclusive, matching `_MAX_LEN`'s fail-closed convention.

### Low

#### REV-00008-LOW-01 — STEP-04's objective ("fast at long inputs") is a performance hypothesis with no decision rule

- **Location:** `docs/plans/00006-Review_00007_to_v2.0.0.md` §11 STEP-04 objective and test-or-evidence-first; §9 `PLAN-00006-REQ-04`/`REQ-05`; `rust/fpr-ff1-rust/Cargo.toml` (`num-bigint = "0.4"`)
- **What / Why / Suggested fix:** The Python speedup measured in review 00005 rides CPython 3.12's `_pylong` divide-and-conquer division; the Rust port's STR direction depends on `num-bigint` having the equivalent. It does — `num-bigint` 0.4.8 `division.rs:216-346` switches to Burnikel–Ziegler above a 64-limb threshold — so the outcome is likely favourable, and its `from_radix_be`/`to_radix_be` cannot be used above radix 256 (`convert.rs:146,177`), so a hand-written D&C is indeed required as the plan says. But the plan asserts the objective and only "records" the result; plan 00003 STEP-13 had a pre-committed park rule for the same kind of claim. Add one: after STEP-04, `just bench` must show `rust ≤ python` at n=20,000 on radix 10 and 256 (or a stated multiple); if not, the Builder escalates with numbers and the README keeps crossover guidance rather than dropping it. Also state that the Rust threshold constant mirrors Python's `_D_C_THRESHOLD = 64` by name and comment, so a reviewer comparing the two cores sees the same dispatch.

#### REV-00008-LOW-02 — REQ-01 should add a structural attribute-parity test and fix the two sibling tests that use the same hiding pattern

- **Location:** `docs/plans/00006-Review_00007_to_v2.0.0.md` §9 `PLAN-00006-REQ-01`; `src/fpr_ff1/_ff1.py:184` (comment: "the constructor and `__setstate__` -- and they must not drift"); `tests/test_backend_dispatch.py:263-279` (`test_corrupt_unpickled_backend_raises`, `test_non_str_unpickled_backend_raises`)
- **What / Why / Suggested fix:** MAJ-01 is an instance of a class — an attribute added to `__init__` but not to `__setstate__`. The plan fixes the instance and the one test that hid it. Two more tests construct their destination with `FF1(key=_KEY, radix=10)` before calling `__setstate__`; they assert raises so they are not hiding a defect today, but they will hide the next one. Add to REQ-01: (a) restore onto `FF1.__new__(FF1)` in all three tests; (b) a structural test — `set(vars(pickle.loads(pickle.dumps(FF1(...))))) == set(vars(FF1(...)))` for a python instance and, under `@requires_rust`, a rust instance — so any future `__init__`-only attribute fails immediately. This is the test form the `_ff1.py:184` comment is asking for.

#### REV-00008-LOW-03 — Three checklist sub-items did not survive the review-to-plan translation

- **Location:** `docs/plans/00006-Review_00007_to_v2.0.0.md` §9 `PLAN-00006-REQ-08`, `REQ-09`; review 00007 `STABLE-10`, `STABLE-11`, `STABLE-12`
- **What / Why / Suggested fix:** (1) STABLE-11: "run the packaged tests from an unpacked sdist with the documented test dependencies" — REQ-09 proves the sdist *installs* but never runs its shipped `tests/` (the sdist ships them precisely so a downstream packager can; `pyproject.toml` comments make that promise). Add it to STEP-10 task 2. (2) STABLE-10: "record the actual compiler version used" — the channel pin is `stable`; the work log should capture `rustc --version` from the release build so the artifact is reproducible-in-kind. Add to STEP-10/12 evidence. (3) STABLE-12: "without implying … 100% Rust line coverage from Python's coverage result" — REQ-08 omits this; the README/CHANGELOG say "100% line and branch coverage" next to "both backends", and a reader can conflate them. Add a one-line clarification target to STEP-08 (Python coverage is measured; the Rust core is covered by the dual-backend suite and `cargo test`, not by a line-coverage figure).
