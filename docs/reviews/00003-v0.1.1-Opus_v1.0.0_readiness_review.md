# fpr-ff1 — v1.0.0 Release Review

> [!success] Headline
> The **algorithm is not the risk here**. The conformance evidence is stronger than most cryptographic libraries on PyPI carry, and I verified it independently rather than taking the README's word for it. The gaps that remain are packaging, lifecycle and one security-policy contradiction — all of them cheap to close, but several of them are the kind that are awkward to fix *after* a `1.0.0` tag freezes the contract.

**Recommendation: do not tag `v1.0.0` yet.** There are 7 blockers, all small. Roughly a day's work, then ship.

## 2. Correctness review — the FF1 core

I read `_ff1.py` line by line against SP 800-38G Algorithm 7/8 and found **no algorithmic defects**.

Specifically confirmed correct:

- **Step 3 `b`** uses `((radix**v - 1).bit_length() + 7) // 8`, derived from `v` not `u`. This is exactly `ceil(ceil(v·log₂ radix)/8)` with no float anywhere — the Bouncy Castle bug class is genuinely closed, and the AST scan in `test_exact_arithmetic.py` keeps it closed.
- **Step 5 `P`** is the correct 16 bytes: `[1,2,1] || [radix]³ || [10] || [u mod 256] || [n]⁴ || [t]⁴`.
- **Step 6.i pad** `(-(t + b + 1)) % 16` ✓.
- **Step 6.iii `S`** is `CIPH_K(R ⊕ [j]¹⁶)` — a single forward-cipher block, not a PRF, with `j` XORed rather than concatenated. This is the defect fixed in 0.1.0 and it is fixed correctly.
- **Step 6.v parity** `m = u if i even else v` is shared by both directions, so the mirrored-decrypt bug cannot occur.
- **Decrypt Q-source length**: I traced the A/B length alternation across all ten decrypt rounds. `NUM_radix(A)` always fits in `b` bytes because `len(A) ≤ v` at every round. No latent `OverflowError`.
- **`_min_length`** terminates correctly on the exact boundary (radix 10 → 6, radix 2 → 20).

> [!tip] One structural observation worth acting on
> The cached ECB encryptor — the sole source of the documented thread-safety hazard — is **only touched when `d > 16`**. I computed the threshold per radix:
>
> | radix | 2 | 10 | 16 | 36 | 62 | 256 | 65535 |
> |---|---|---|---|---|---|---|---|
> | first `n` with `d > 16` | 193 | **57** | 49 | 37 | 33 | 25 | 13 |
>
> For the archetypal FPE workload — a 16-digit PAN, a 9-digit SSN — the shared mutable context is **never entered at all**. Which means the thread-safety bug is dormant in exactly the cases people will test with, and wakes up on long inputs in production. See [[#H2]] for why that changes my recommendation from "document it" to "fix it".

## 3. Findings

Severity: 🔴 blocker for 1.0.0 · 🟠 high · 🟡 medium · ⚪ polish

### 🔴 B1 — Version and maturity classifier still say pre-release

`pyproject.toml` carries `version = "0.1.1"` and `"Development Status :: 4 - Beta"`. A `1.0.0` shipping as Beta on the PyPI sidebar undercuts the entire trust argument the README makes.

**Fix:** bump `version`, change the classifier to `"Development Status :: 5 - Production/Stable"`.

### 🔴 B2 — No `__version__` on the package

```python
>>> import fpr_ff1; hasattr(fpr_ff1, "__version__")
False
```

There is no `__version__` anywhere in `src/`, `tests/` or `docs/`. For a library whose entire value proposition is "your ciphertext is conformant", a caller who needs to record *which build produced this data* has to reach for `importlib.metadata` and hope the distribution is installed. Add it now, while it can be documented as part of the stable surface.

**Fix:**
```python
from importlib.metadata import version
__version__ = version("fpr-ff1")
```
…and add `"__version__"` to `__all__`.

### 🔴 B3 — Exception messages echo plaintext into logs

This is the finding I would push hardest on, because the package **contradicts its own security policy**.

`SECURITY.md` lists as explicitly *in scope*:

> Anything that causes plaintext or key material to be logged, raised in a message, or otherwise exposed.

Observed behaviour:

```text
>>> ff1.encrypt("12345X")
ValueRangeError: character 'X' at index 5 is not in the alphabet

>>> ff1.encrypt_numerals([1,2,3,4,5,42])
ValueRangeError: plaintext[5]=42 out of range for radix 10
```

The offending **value** and its **position** both go into the exception message. In the intended deployment — an FPE library sitting in a pipeline over PANs, SSNs, dates of birth — that message lands in Sentry, CloudWatch, or a Spark driver log, and a fragment of the plaintext lands with it. A batch job with a dirty column will emit thousands of them.

The 0.1.0 changelog frames the character in the message as an improvement over the bare `KeyError`, and for debuggability it is. But it was the wrong trade for this library's threat model, and `1.0.0` is the last cheap moment to reverse it.

**Fix:** keep the index and the failure kind, drop the value.

```text
character at index 5 is not in the alphabet
plaintext[5] is out of range for radix 10
```

Cost is near zero: only 5 `match=` assertions exist in the whole suite and none of them assert on these two messages. If the debuggability loss stings, gate it behind an explicit opt-in (`FF1(..., verbose_errors=True)`) that is off by default and documented as unsafe for production logs.

### 🔴 B4 — `requires-python` upper cap breaks in four weeks

```toml
requires-python = ">=3.12,<3.15"
```

**Python 3.15.0 final is scheduled for 1 October 2026** — 3.15.0rc2 shipped on 1 September and is the final planned release candidate. If `1.0.0` ships this month with that cap, it becomes uninstallable on 3.15 roughly four weeks later — and because *every* published version carries the same cap, users on 3.15 get a hard resolution error rather than a fallback.

The README defends the cap as "matching the tested matrix", and the intent is sound. But the cost is borne by users, not by you: a capped `requires-python` is a claim that future Pythons *don't* work, which you can't know, rather than that they're untested, which is what a classifier communicates. PyPA guidance discourages upper-bounding `requires-python` in libraries for exactly this reason. The counter-argument — that a silent breakage on an untested interpreter is worse than a loud install failure — is legitimate, but it is weaker for a pure-Python package with one dependency and no C extension.

**Fix (pick one, in order of preference):**
1. Drop the upper bound entirely; keep the classifiers as the statement of what's tested.
2. Keep the cap but add `3.15` to the CI matrix **now** with `allow-prereleases: true`, and ship `1.0.0` with `<3.16`.

Either way, `3.15` should be in the matrix before you tag.

### 🟠 H1 — `FF1` instances cannot be pickled or deep-copied

```text
>>> pickle.dumps(ff1)
TypeError: cannot pickle 'cryptography...CipherContext' object
>>> copy.deepcopy(ff1)
TypeError: cannot pickle 'cryptography...CipherContext' object
```

Given the audience — FPE is overwhelmingly used in batch data processing — this is a real usability wall:

- `multiprocessing` with the **spawn** start method (the default on macOS and Windows, and on Linux from 3.14) cannot pass an `FF1` to a worker.
- `ProcessPoolExecutor` likewise.
- **PySpark cannot broadcast an `FF1` instance**, so every UDF invocation has to reconstruct it or lean on a module-level singleton.

The cause is the cached `CipherContext` in `_Aes`, which is opaque Rust state. The fix is mechanical, additive, and worth doing before the surface freezes:

```python
def __getstate__(self) -> dict[str, object]:
    state = self.__dict__.copy()
    del state["_aes"]          # rebuild rather than serialise
    return state

def __setstate__(self, state: dict[str, object]) -> None:
    self.__dict__.update(state)
    algorithm = algorithms.AES(self._key)
    self._aes = _Aes(...)
```

> [!warning] Consider this alongside [[#H3]]
> `__getstate__` will serialise `self._key` — the key crosses a pickle boundary and may hit a temp file or a socket. That is inherent to making the object picklable and is the caller's decision to make, but it must be **documented explicitly** in `SECURITY.md` rather than discovered.

### 🟠 H2 — Thread safety: fix it rather than document it

The documentation of this is genuinely excellent — class docstring, README, `docs/configuration.md`, changelog. But documentation is a weak control when the failure mode is **silently wrong ciphertext** rather than an exception, and when (per §2) the hazard is invisible for every input short enough to be in someone's unit tests.

The good news is that fixing it costs almost nothing. The shared context is used only in the `d > 16` branch, and a fresh ECB encryptor measures **~3 µs** against a ~63 µs baseline operation.

**Fix:** build the encryptor lazily, inside the expansion loop, instead of caching it on the instance:

```python
# in _ff1(), inside the round loop, only when needed
s_block = r_block
if len(s_block) < d:
    ecb = Cipher(aes.algorithm, modes.ECB()).encryptor()
    j = 1
    while len(s_block) < d:
        ...
```

That makes the cost **exactly zero** for `d ≤ 16` (the common case, which never allocates one) and ~3 µs for long inputs, which already cost hundreds of microseconds. `algorithm` and `cbc_zero_iv` are immutable value objects and `_prf` already builds a fresh CBC encryptor per call, so removing this one context leaves **no shared mutable state at all** — and you get to delete the caveat from four documents and turn it into a guarantee. For a 1.0 that is a materially better contract.

### 🟠 H3 — `self._key` is written and never read

```text
src/fpr_ff1/_ff1.py:182:  self._key = key   # ← only occurrence
```

The attribute has no reader. It holds a second live reference to key material on every instance for no functional reason, which is a slightly odd look in a package whose `SECURITY.md` has a section on key material. Either delete it, or keep it deliberately for [[#H1]] and say so in a comment.

### 🟠 H4 — Unpinned Actions in a workflow with publish rights

`publish.yml` grants `id-token: write` and pushes to PyPI. It calls:

- `actions/checkout@v4`
- `astral-sh/setup-uv@v5`
- `actions/upload-artifact@v4`
- `pypa/gh-action-pypi-publish@release/v1` ← a **floating branch ref**, not even a tag

A mutable tag or branch in a publish path means a compromised upstream action inherits your OIDC token. Given the `tj-actions/changed-files` incident, pinning to full commit SHAs is now baseline practice for any workflow that can publish.

Separately, `ci.yml` installs gitleaks by piping a GitHub release tarball straight into `sudo tar` with **no checksum or signature verification**.

**Fix:** pin every action to a 40-char SHA with the version in a trailing comment; verify the gitleaks tarball against its published checksum; add `dependabot.yml` with the `github-actions` ecosystem so the SHAs stay current.

### 🟠 H5 — The published artifact is not the artifact CI tested

`publish.yml` runs `ci.yml` as a gate (good), but then **rebuilds** with `uv build` in a fresh job rather than downloading the `distributions` artifact the `build` job already produced and `twine check`ed. Two builds, and only one was verified.

Also, `workflow_dispatch` on `publish.yml` means anyone with write access can publish from an arbitrary ref without cutting a release.

**Fix:** `actions/download-artifact` from the gate run and publish that; drop `workflow_dispatch` or restrict it to a protected environment with required reviewers.

### 🟠 H6 — The differential oracle is a single point of failure

The correctness evidence for radices 2, 16, 32, 62, 256 and 65535 rests entirely on `ubiq-security-fpe==2.0.1.1` — a **deprecated, unmaintained** package. `FPR_FF1_REQUIRE_ORACLE=1` correctly turns a missing oracle into a hard failure, which means the day it stops installing (a yank, a `setup.py` that breaks on 3.15, a wheel-less sdist that won't build) your CI goes red across all nine legs and your strongest evidence evaporates. `docs/backlog.md` notes the risk but parks it.

**Fix — and this one is cheap:** commit a frozen KAT file **generated by the oracle**, with a provenance header recording the oracle version and generation date. Keep the live differential run as the primary check and let the frozen vectors be the fallback when the oracle is unavailable.

This does *not* violate the `AGENTS.md` rule against self-authored vectors: the values come from the independent implementation, not from `fpr-ff1`. The rule exists to stop you locking in your own bugs; oracle-derived vectors do the opposite. It converts a perishable dependency into a durable artifact, which is the whole point.

### 🟡 M1 — Formatter drift will break CI on the next `just lock`

`ruff>=0.12.0` is unpinned in `[dependency-groups] dev`; `uv.lock` currently holds **0.15.20**, which is why CI is green. Verified:

| ruff | `format --check .` |
|---|---|
| 0.15.20 (locked) | 16 files, all formatted ✅ |
| 0.16.6 (current) | 27 files, **2 would be reformatted** ❌ |

Ruff 0.16 formats Python code blocks inside Markdown. `README.md` (the migration example) and `AGENTS.md` (the API sketch) both fail. The next `just lock` turns CI red for reasons unrelated to any code change.

**Fix:** run `ruff format` under 0.16.x now, commit the result, and raise the floor to `ruff>=0.16` so the lock and the constraint agree about which formatter's opinion governs.

### 🟡 M2 — `pre-commit` is a dev dependency with no config

There is no `.pre-commit-config.yaml` and no `just` recipe that invokes it. Either add the config (wiring `ruff`, `ruff-format` and `gitleaks`, which would catch M1 locally) or drop the dependency.

### 🟡 M3 — Nothing installs and imports the built wheel

CI tests the source tree via `uv sync`. A packaging error — a missing `py.typed`, a bad `packages` entry — would pass the whole matrix. The wheel is currently correct (I checked), but nothing *keeps* it correct.

**Fix:** add a job that does `uv build`, `pip install dist/*.whl` into a clean venv, then runs the test suite against the installed package.

### 🟡 M4 — `--cov-fail-under=100` in `addopts` is hostile to downstream packagers

Since the sdist ships the tests, a Debian or conda-forge packager running `pytest` from the unpacked sdist hits the coverage gate — and fails outright if `pytest-cov` isn't installed. The `justfile` comment shows this is deliberate ("so a bare `pytest` is gated too"), which is a reasonable call for contributors and an unreasonable one for redistributors.

**Fix:** move the coverage flags into a `just coverage` recipe or a separate `pytest-cov.ini`, and note the invocation in `docs/developer-guide.md`.

### 🟡 M5 — Public surface is thin at the moment it freezes

The public API is `encrypt`, `decrypt`, `encrypt_numerals`, `decrypt_numerals`, `min_length`, `max_length`. Worth considering before the freeze:

- Read-only `radix`, `alphabet`, `tweak` properties. Callers writing generic pipeline code currently have to track the radix alongside the instance.
- A `__repr__`. The default (`<fpr_ff1._ff1.FF1 object at 0x...>`) is safe but uninformative; an explicit one that shows `radix` and `min_length` and **provably never** touches key material is better than relying on the default staying safe.

Both are additive and could land in 1.1, but a `__repr__` written deliberately is a security-relevant choice worth making at 1.0.

### 🟡 M6 — `cryptography>=44.0.0` floor is higher than the code requires

The package uses only `Cipher`, `algorithms.AES`, `modes.CBC` and `modes.ECB` — APIs stable for many major versions. A 44.0 floor (Nov 2024) is a hard barrier for exactly the enterprise environments that most want FPE and are most likely to be pinned. `uv.lock` resolves to 50.0.0, so the floor isn't buying test coverage either.

**Fix:** lower to the oldest version you're willing to claim (`>=42` is defensible), or add a one-line comment in `pyproject.toml` justifying 44 so it isn't re-litigated.

### 🟡 M7 — No README badges

No CI status, PyPI version, supported-Python or licence badges. For a package asking to be trusted with cryptographic correctness, a green CI badge at the top is the cheapest possible trust signal.

### 🟡 M8 — Missing community and automation files

No `CONTRIBUTING.md`, no `CODE_OF_CONDUCT.md`, no issue or PR templates, no `.github/dependabot.yml`. `SECURITY.md` is excellent, which makes the absence of the others more conspicuous.

### 🟡 M9 — SECURITY.md publishes measurements with no harness

The timing table (`+0.8%` … `+2.6%`) is a specific, falsifiable empirical claim, and it's the right way to write that section. But the benchmark that produced it isn't in the repository, so nobody — including future-you — can reproduce or re-run it after a change.

**Fix:** commit `benchmarks/timing.py` and a `just bench` recipe; reference it from the table.

### 🟡 M10 — No published performance characteristics

Measured here, CPython 3.12, single core:

| Input | Throughput | Per numeral |
|---|---|---|
| 6 numerals, radix 10 | ~16,000 ops/s | 62.6 µs/op |
| construction | ~114,000 /s | 8.8 µs |
| n = 100 | — | 2.5 µs |
| n = 1,000 | — | 2.8 µs |
| n = 5,000 | — | 8.7 µs |
| n = 20,000 | — | 32.4 µs |

The per-numeral cost climbs sharply past ~1,000 because `_num_radix` / `_str_radix` are quadratic in the big-integer conversions. That is inherent and fine — but someone sizing a nightly job over 50M rows needs the number, and the 2.0 roadmap's "accelerated backend" is much easier to justify against a published baseline.

Minor related nit: `radix**m` is recomputed on each of the ten rounds inside `_ff1`. Both values (`radix**u`, `radix**v`) are loop-invariant; hoisting them is free.

## 6. Suggested release sequence

1. Land **B3**, **H1**, **H2**, **H3** together — they are the only changes that touch runtime behaviour, and all four are things you cannot do cheaply once 1.0 sets the contract.
2. Land **B4** + **H4** + **H5** + **M1** as one CI/supply-chain commit; confirm the full nine-leg matrix is green, plus a tenth 3.15 leg.
3. Land **H6** and **M3** — the two changes that protect the evidence rather than the code.
4. Documentation sweep: **B1**, **B5**, **B6**, **B7**, plus **M7**, **M9**, **M10**.
5. Tag `v1.0.0`, publish the GitHub release, let Trusted Publishing fire.
6. Confirm on PyPI: classifier reads Production/Stable, `requires-python` is right, provenance attestations are present on both artifacts.

> [!question] The one judgement call I'd flag back to you
> **B3** and **H2** are both cases where the current behaviour was a *deliberate* decision, documented and defended — richer error messages, and a cached context for speed.
